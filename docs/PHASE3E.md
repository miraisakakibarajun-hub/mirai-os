## 4. 将来移行設計

|移行対象|分類|条件|
|---|---|---|
|利用者ID・氏名・日付|人の確認後、自動移行可能|正本・重複・法人事業所を確定、旧ID→新ID台帳|
|職員・Auth|人の確認後移行|旧メールだけで権限推定しない。新規発行フローを通す|
|担当関係|人の確認後移行|開始／終了／現在有効を確認。旧作成者を自動で現在担当にしない|
|構造化された4種記録|自動移行可能（変換仕様確定後）|利用者、作成者、実施日、JSON項目・版を照合|
|紙・PDF・自由形式文書|手入力または人の確認後移行|OCRを正本とみなさず、実データ処理は別承認|
|計画・過去版|人の確認後移行|原版・日時・承認証跡が必要。証跡不足は下書き／未確認として隔離|
|旧AI下書き・途中成果|要判断／移行不要候補|自動採用しない。原本保全を継続|

移行実行前に対象・件数・チェックサム・対応表・エラー一覧をレビューする。バッチID＋元データハッシュを固定、同一再実行はスキップ、内容の変わった同一バッチは停止。1トランザクションで適用し、不整合は全体ロールバック。復旧は専用隔離DBを再構築して保全点へ戻す。本番でTRUNCATEや旧Migrationへの巻戻しはしない。
今回のPGliteリハーサルは架空利用者1・職員1・担当1・計画1の変換、日付／JSON／件数／権限／監査、重複防止、承認状態を捏造しないことを検証する。実際の移行元形式や全過去版を網羅した移行ツールではない。

|---|---|---|

|Auth|Authデータを含む保全＋設定台帳、DBと同じ保全点|架空復旧アカウントでログイン・担当／停止。実復旧ではセッション失効も確認|

DBバックアップにStorageの実体やカスタムロールのパスワードは含まれない。Authの外部メール／OAuth／許可URL、プロジェクト鍵もMigrationとは別。鍵はバックアップ本体と分離し、復旧権限を限定する。[Supabaseバックアップ](https://supabase.com/docs/guides/platform/backups)

今回の復旧スクリプトはLinux CI、固定コンテナ名、127.0.0.1、架空Authドメイン・架空法人を検証し、環境指定引数を受け付けない。全Migration適用後にpublic／mirai_private／Authの架空データを復元し、全業務テーブル比較、パスワードログイン、PostgREST、ブラウザーまで確認する。ダンプには架空Authハッシュ等があるためCI artifactへ公開しない。CI終了時に隔離スタックを停止する。
RPO24時間は日次ジョブの最終成功監視と失敗時対応が成立して初めて達成できる。今回の一点復元試験だけでは運用RPOを証明しない。RTO実測は少量架空データ・CI環境の値であり、本番の認証／DNS／鍵復旧・担当者到着時間を含まない。PITRは有料・Small以上等の条件があるため契約せず、より短いRPOが必要になったら費用と当番負担を再審査する。

## 6. 新規職員の初期登録フロー案

1. 事業所の責任者が氏名・法人・事業所・業務ロール・期間・必要担当を申請。
2. 別の業務管理者が必要性と範囲を承認。申請者自身の昇格・自己承認は不可。別承認者不在なら処理停止。
3. 技術担当は承認番号に紐づくAuth招待／発行だけを行う。事業所・業務ロールを単独決定しない。
4. 初期staffは停止状態で作成し、承認内容どおりの法人・所属期間・ロールを付与。想定外のメール重複／既存Auth不一致は停止。
5. 別管理者が本人確認と設定照合を終えて有効化。初回ログイン・MFA／パスワード手順を確認し、担当を明示設定。
6. 誰が申請・承認・発行・有効化したかを本文や秘密値なしで監査。途中失敗時は停止状態を維持、同じ申請番号は重複発行しない。

今回このフローは設計のみ。実在Auth作成、招待メール、外部通知なし。初期の管理者を誰が承認するか、責任者・代替者の選任はAI本部判断。
