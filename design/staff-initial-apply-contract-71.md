# INITIAL-APPLY-CONTRACT-71／初回認証許可の適用処理契約

2026-10-11。設計責任者・承認確認先：榊原純。AI-2026-044は採番候補。D02・D05・D12／初回許可70の次工程。設計案、未実装、実環境未適用。024・043原本は変更しない。

## 確定と保留の境界

確定：権限付与・変更・停止の管理担当は榊原純。ご自身の権限付与・拡大・停止解除は城戸裕子が承認。初期代理承認なし、不在時は承認待ち。人物・所属・契約・業務役割・システム権限は別管理。初回パスワード変更と業務権限初期設定は別工程。

未決：初回認証許可の承認者と初期登録実施資格、初期技術操作主体の発行根拠、具体的な許可期限、取消手続。承認後に承認者の権限が失効した場合や法人規則版が変更された場合の再審査範囲も既存D05で未決。これらを新しく確定しない。方針未確定の場合、登録処理はPOLICY_UNDECIDEDとして保留する案。設計作業は進めるが、初回許可の実登録を開始しない。

## サーバー内部の処理契約案

適用入口候補名：apply_initial_admission_v1。通常ログインruntimeとは別の適用主体・専用DB接続で呼ぶ。実HTTPルート、DB関数、専用roleは今回作成しない。

| 区分 | 契約案 |
| --- | --- |
| 呼出入力 | application_id、expected_request_revision_id、attempt_id、operation_id、lease_token。全て対象選択・競合確認用。tokenはサーバー内部のみ |
| 固定設定 | 発行元issuer、対象org_id、技術actor、処理種別INITIAL_AUTH_ADMISSION_APPLY。実行DB接続とレビュー済み設定から解決 |
| 読取根拠 | 固定対象の型付き申請版70、現在申請ポインター、承認判断と根拠、影響確認、適用・現在試行・操作、人物／法人／アカウント／認証制御、現在停止、関連方針・認可版 |
| 成功出力 | 適用ID、許可ID、対象申請版、確定時刻、APPLIED。外側COMMIT確認後のみ |
| 確認済み再送 | 同一適用・申請版・判断・許可・成功監査を確認できた場合にALREADY_APPLIED。同じ処理の新規許可を作らない |
| 確認済み拒否 | 固定分類とBLOCKED／CONFLICT／LEASE_LOST。成功許可・成功監査を作らない |
| 保存結果不明 | PERSISTENCE_UNCONFIRMED。APPLIEDを返さず、同一適用IDで照合する |

入力の人物・法人・epoch・承認者・APPROVED値・SUCCEEDED値・現在時刻は採用しない。業務肩書きやSERVICE actorの存在だけから実行権限を推定しない。IDの指定は許可を意味しない。外部Auth作成・パスワード変更・メール交付・Cookie発行を、このDB適用処理へ混在させない。

承認時の事実は後から書き換えない。適用時に規則の更新を発見した場合、既存未決方針を勝手に「承認は永久有効」または「常に再承認」と解釈しない。

## トランザクションとロック順の設計案

1. 固定実行設定と技術資格を解決する。外部入力の設定値を利用しない。
2. 同一申請・適用の成功証跡がすでにあるかを読んで、再送候補または未実施候補を識別する。読取だけで成功を返さない。
3. 影響する認証・認可・法人規則のfenceを取得する。既存63の法人認証キーはcompact JSONのSTAFF_AUTH_ORG_V1／issuer／org_idであり、同じキーを利用する。変更を適用する経路の排他と判定経路の共有を統一する。全法人に影響するACCOUNT_GLOBAL・epoch変更の共通境界と取得順は未実装のため、本番採用条件として保留する。
4. 固定設定・主体、申請管理行→申請版／判断→適用→現在試行→操作→影響確認の必要行、人物→アカウント→認証／認可controlの必要行を、レビューで固定した全経路共通の順序でロックする。法人・方針・承認主体の依存も同じ順序表に含める。複数の同種行はUUID順とする案。これは71の候補順であり、63の現在行ロック順とすべての更新経路を統合した実装は未完成。
5. すべてのロック取得後にDBの新しい時刻で現在状態・方針・期待版・停止・リースを評価する。ロック待ち前の時刻を再利用しない。提示リースtokenのハッシュ照合は実処理が行い、70の「ハッシュ形式が正しい」検証で代用しない。
6. 新規時は、初回許可70、成功適用、成功試行と確定時刻、成功操作、成功監査を保存する。初回変更の完了や業務権限の発行は行わない。70の遅延整合検証が成立する最終状態へ、外側COMMITまでにそろえる。
7. 成功確定操作の直前にも新しいDB時刻でリースと許可期限を照合する。成功確定時点をリース判定の線形化時点とする案。COMMITそのものが期限前に返る保証とは区別する。初回ログイン／既存セッション確認はその都度現在の許可期限とepochを再評価するため、確定後に期限切れになった許可を利用しない。
8. 外側COMMITを確認して成功を返す。COMMIT不明なら新しい許可IDで再実行せず照合へ回す。

取消・適用・リース回収は同じ申請／適用行とfenceに参加する必要がある。71の順序と70のコミット時共有ロック、型付き申請作成時の申請版ロックを実装前に統合する。番号の比較や一つの関数だけのadvisory lockで、参加しない既存更新経路との競合を解決したとはしない。DBトランザクション内で外部HTTPを呼ばない。

## 再送・結果不明・取消

| 状況 | 契約案 |
| --- | --- |
| 同一成功適用の再送 | 全固定参照と成功監査を照合しALREADY_APPLIED。これは過去の登録事実であり現在ログイン可能の保証ではない |
| 同じ適用IDで別申請版を指定 | CONFLICT。既存結果や許可を上書きしない |
| 実行中の試行が別workerへ回収済み | 旧tokenではLEASE_LOST。現試行・監査を更新しない |
| COMMIT不明後の再送 | まず既存証跡を照合。成立確認なら既存結果、未確認ならPERSISTENCE_UNCONFIRMED。新規許可を作る根拠にしない |
| 成功後の期限切れ／epoch変更 | 許可・承認事実は保存し、現在認証判定で利用不可にする |
| 申請取消と適用が競合 | 同じfenceと管理行で直列化する。取消済みなら適用拒否。成功後の取消を許可取消へ自動転用しない |
| 許可を取消する業務 | 具体手続・承認条件は未決。epoch変更が旧許可を利用不可にする構造は70で確認したが、正式取消手続として確定しない |

再送照合も接続主体の現在の照合資格と固定範囲を必要とする。成功済みのため期限切れleaseを再び有効扱いするのではなく、既存結果の参照処理として分ける。

## 監査候補

成功イベントINITIAL_ADMISSION_APPLIEDは、event_id、admission_id、application_id、request_revision_id、decision_id、attempt_id、operation_id、実行actor、対象account/person/issuer/org、auth_epoch、参照した方針版・認可版、DB確定時刻を保持する案。適用結果と同一トランザクションで追記し、更新・削除不可。業務本文・パスワード・外部Auth token・lease_token平文・provider応答本文を記録しない。

拒否／結果不明は成功イベントと分け、固定分類と相関IDだけを技術記録へ残す。認可されていない対象人物名やログインIDをHTTPへ返さない。監査が保存できない場合に許可だけを成功扱いしない。成功監査DDLと信頼できる書込関数は未実装。
